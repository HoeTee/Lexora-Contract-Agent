三个容易混淆的边界

从用户提交，到拿到批注合同

Web 直接调用 enqueue_review_job；CLI 通过 API 提交。两条入口汇入同一 Celery 业务执行链，不是 Web 在内部调用一次公共 API。

加 worker 为什么不等于加模型容量？

下方是教学示意，不读取或修改真实配置，不是吞吐量预测。初始数值取自示例 Compose 与示例配置。

① Celery：整份合同的执行槽

② Orchestrator：每个合同自己的要点槽

③ Redis：所有相关进程共享的模型池

演示假设：所有活动合同都在要点审查阶段，每个活动要点恰好同时申请一个所选类型的请求。真实代码有先后依赖、工具调用和索引线程池，因此这个演示只说明上限与排队，不能把三个模型池的容量相加当作合同并发。

还有索引内部的并发

DocxIndex 索引增强使用线程池，向量按批次调度。当前构建调用把对应模型池容量值传入局部并发参数；每次实际发送仍会领取 Redis 槽。

共享的前提

Redis 地址、DB、key 一致才共享容量。复制 Compose 项目时，即便容器名独立，若模型池仍指向相同 Redis/key，它们仍互相限制。

超时是另一个维度

模型等待额度、单次请求时钟、整份合同截止时间分别控制等待和执行。放大 concurrency 不会自动扩大它们。

一条模型请求经过哪些控制点？

累计等待预算

跨重试累计等待模型槽。默认示例为 180 秒。等待时尚未开始这次 HTTP 请求时钟。

一次请求时钟

非流式默认示例为 60 秒总请求时间；流式为有效内容进展间的空闲上限。重试启动新时钟。

合同总截止时间

示例为 1800 秒，由 worker 设置。即使流式持续输出或一直重试，也不能突破合同截止时间。
