## 用户确认的改动

恢复最多三次模型输出机会，以及失败要点最多两次完整尝试。实现采用现有统一发送预算：`workflow.model_call_max_retries` 从 1 改为 2，并恢复 `workflow.criterion_retry_max_attempts: 2`。

网络重试和 JSON/schema 修复仍共用最多三次发送；不恢复旧版多层独立重试叠加。每次模型操作仍共用 60 秒，合同硬时限仍为 1800 秒。第二次要点尝试使用新的模型操作预算，但不能延长合同硬时限。成功结果继续复用，失败历史保留。

本轮不改提示词、schema、检索和业务审查规则。三个 worker 及共享模型上限 5/3/10 保持不变。

## 验证计划

1. 验证统一控制允许第三次格式修复，但不会发送第四次，也不会重置操作截止时间。
2. 验证要点第一次失败、第二次成功时保存 attempt=2，失败历史仍保留；两次均失败时结束，成功状态不被错误覆盖。
3. 更新配置说明及迁移规则，使重新保留的配置能被加载和审计。
4. 沿用上一轮合同和其余配置，三个 worker 同时执行三份完整任务；比较 H18、全任务要点质量、重试与超时、名额结束状态。

实际请求仍使用本地现有阿里云域名服务，不能作为公司内网生产或测试服务的性能验证。

### H18 的边界

H18 本轮仍为两次完成、一次失败，与恢复前相同。两份完成的 H18 都没有用到新增的第三次格式发送或第二次要点尝试，不能把它们的完成直接归因于新增额度。

第 2 次 H18 首轮把 p135 电话和 p158 通用附件效力声明判为 not_found，却没有相应 edit 批注；业务修订耗尽后，确实启动了第二次完整尝试。第二次 SubAgent 请求未返回响应，名额等待 0.000650 秒、实际请求 59.961091 秒、累计 60.049681 秒，最终超时。当前 60 秒统一预算正常生效，增加发送次数不能在预算耗尽后再发请求。

第 1 次经反思删除误报后合规；第 3 次经一次 JSON 修复和覆盖修复后合规。三遍仍缺少正文末尾 p163—p166 四项附件目录，第 2 次甚至没有取得实际“设备配置清单”标题。因此，完成项增加不代表取材和业务判断缺陷消失。
