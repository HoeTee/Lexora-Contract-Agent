结论：配置已生效，四次发送带来了两次汇总操作恢复，但未提高整体要点完成率。H18三次都完成，均未用第四次发送，不能据此认定H18被新配置修复。

本轮按用户批准，仅将本地 `config.yaml` 的 `workflow.model_call_max_retries` 从2改为3，即首次外再允许3次发送，总上限4次。此字段同时约束网络重试与JSON/schema修复，仍共用一次模型操作的60秒预算，不是每次发送各有60秒。

其余业务配置、合同和源码保持：要点总尝试2次、反思最多10轮、每合同要点并发2、全局LLM/embedding/reranker并发5/3/10，三个Celery worker各并发1，DB0队列、DB2模型协调，合同硬时限1800秒。测试配置逐字段与三发送基线相比只有重试上限一处差异；两轮测试均开启详细日志，本地日常配置的logging.detailed=false保持。

本轮为本地隔离Docker API/Celery实测，使用本机配置中的阿里云域名模型地址；不是公司内网部署验证，不能据此评价公司内网服务。模型名称、地址与凭据未更换。依赖镜像lexora:latest；当前工作区源码只读挂载到/app；本轮宿主机目录的data/profiles/logs分别挂载到/app对应目录并保留。

- 第1、2份各一次索引摘要index-summary-batch2-node-body，第四次仍超过200 tokens，最终走回退。
- 三个H18的所有逻辑操作最多发送1—3次，均未用第四次。第2份H18经历4轮业务反思，是原有max_reflection_rounds控制的循环，与第4次发送不同。

H18最终三份均无issue：p41判匹配、p135电话段/p158通用附件效力声明判不适用，证据字段为真正的JSON null/null。四条H18初始审查请求（第3份因schema重发有两条）仍未获得p163—p166正文末尾附件目录。第2份反思以附件2—4无具体正文引用为由通过，但实际目录缺失于上下文。因此completed和COMPLIANT不能证明附件核查覆盖完整，原有提示词契约与检索遗漏仍待修复。
