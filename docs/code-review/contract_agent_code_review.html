03 / CONCURRENCY ARCHITECTURE

并发控制架构

图 1：并发调度与并发限制分层。Celery、criterion semaphore、线程池和 Redis semaphore 不是同一个作用域。

三类容易混淆的机制

调度

create_task、gather、Celery 把工作变成可并发任务；它们不保证最终资源并发数。

局部限制

进程内 asyncio.Semaphore 或 BoundedSemaphore 只约束同一对象或同一进程内的调用。

全局限制

Redis sorted-set 租约跨进程共享，才是多个 worker/container 之间的模型在途请求上限。

05 / TIME & RETRIES

时间、租约、等待与重试关系

图 2：时间参数必须按作用对象区分；队列超时、槽位等待、租约和 HTTP timeout 不能互相替代。

重试放大

DocxIndex LLM 的同步客户端对 429 最多执行 5 次尝试，并使用 1、2、4、8 秒退避；每次尝试都会重新等待全局模型槽。结构化输出校验默认还允许 3 轮完整调用。

DocxIndex complete() 理论配置包络 ≤ 5 × (600s 槽等待 + 120s HTTP) + 15s 退避 = 3615s
complete_model() 理论配置包络 ≤ 3 × 3615s = 10845s
这些是把所有上限同时取满的配置包络，不是实际延迟预测。429 通常会提前返回；缓存命中、有效输出和快速响应都会显著缩短时间。材料不把包络值冒充实测 SLA。

其他乘法层

  • chat_until_valid_json(max_attempts=3)：Agent 结构输出失败时最多 3 次逻辑聊天。
  • criterion_retry_max_attempts=2：一条 criterion 的完整检索、审查和反思链可能整体重跑。
  • max_reflection_rounds=3：非 compliant 结果可能进入多轮 Reflector。
  • Agent 的 OpenAI SDK max_retries=1：具体退避由已安装依赖实现决定；只从项目代码无法确定精确总时间。

Fallback 与反思重检

检索 fallback

只有配置启用、RoutePlan 明确请求且路线仅含可安全扩大的 title/rule 时，才补一次全局语义检索。region/scan/hybrid 不触发。

反思重检

第一轮证据不足后，审查 Agent 以新的缺口 query 再调用 contract_search。它属于新一轮取证，不等同于当前检索的 fallback。

检索设计风险

  • llm_query() 对结构分片仍按顺序循环；内部 BoundedSemaphore 不会让这些分片并发。
  • rerank_matches() 每次调用只产生一个 LLM 请求，函数内新建 limiter 不形成跨 criterion 控制。
  • DocxIndex rerank 使用通用 LLM，不使用配置中的专用 reranker provider。
  • 多 region 的交错合并至少保留每个非空步骤的一项，但最终证据质量仍依赖结构摘要和模型选择。
  • 索引快照持久化用于复现和恢复；在线 retriever 的内存对象仍与单次 MCP 进程生命周期绑定。

09 / OBSERVABILITY

日志、Trace 与问题重放

API events

输入保存、队列提交、worker 开始、模型失败和结果输出等产品事件。禁止记录带签名 query 的 URL。

Trace tree

workflow.run → phase → criterion → llm/mcp 的父子关系、状态和耗时；用于定位卡在哪一层。

Call / route events

模型 request/response 摘要、route plan、step、fallback、候选 node_id 和 semaphore 等待时间。

并发排障建议路径

  1. 先看 task 状态与 worker heartbeat，区分未领取、等待资源和已运行。
  2. 再看 trace 外层阶段墙钟时间，不把并发 criterion 耗时直接求和。
  3. 查看 call log 的 queue_wait_seconds 与 request_seconds，区分槽等待和模型服务耗时。
  4. 查看 route event，确认是否因 scan 批次、结构分片或 fallback 放大调用数。
  5. 把有效配置摘要与日志关联；不能只记录 config.yaml 路径。
当前 DocxIndex 调用已经记录 queue/request timing，但不同 Agent/工具的字段完整度仍需统一核查。评审时应要求每次模型调用都能回答：等待了多久、请求用了多久、占用哪个全局 key、是否重试。

质量评测与验证口径

不能只用“最终报告看起来正确”评估整条 Agent 工作流。建议按故障归属拆分指标：

11 / DEPLOYMENT & CAPACITY

部署边界与容量推演

当前容器边界

  • API：1 个 uvicorn worker。
  • Celery：3 个独立 worker 容器，每个 concurrency 1。
  • Redis DB 0：Celery broker。
  • Redis DB 2：模型 semaphore。
  • 共享 ./data：任务状态、输入、输出、日志、索引快照。

扩容时必须同步复算

  • 增加 worker 会线性提高合同与 criterion 生产并发。
  • 不提高 Redis 模型上限时，新增 worker 更容易停在模型槽等待。
  • 提高全局模型上限前需确认上游服务配额、QPS 和显存容量。
  • 共享数据目录必须支持多个容器一致读写和锁文件语义。
吞吐瓶颈 ≠ max(worker)；吞吐瓶颈 = 各阶段有效服务率中的最小值

在当前配置下，仅增加 Celery worker 数量不会必然提高模型密集阶段吞吐，因为 LLM 全局在途上限仍为 5。反之，只增大 LLM 全局上限也不保证合同吞吐增加，因为合同执行槽仍为 3，且 DOCX 解析、索引和报告生成还会占用 CPU/内存。

12 / REVIEW QUESTIONS

建议在内部评审会上确认的问题

  1. 容量目标：目标是限制全局在途请求、每秒启动次数，还是同时限制两者？当前只有全局在途限制，没有统一全局 QPS limiter。
  2. 合同并发：max_api_concurrent_reviews=100 是否应在队列模式下保留，还是应明确标注只对进程内模式生效？
  3. 模型分类：DocxIndex rerank 应继续使用通用 LLM，还是改用专用 reranker 并消费 reranker semaphore？
  4. 超时策略：Agent 30s 与 DocxIndex 120s 是否是有意区分？是否需要统一的“单次 HTTP、逻辑调用、criterion、任务”四级 deadline？
  5. 等待策略：允许 Celery worker 最多等待模型槽 600s 是否合理？是否应把等待移到不占用合同 worker 的调度层？
  6. 状态语义：queued 是“已进入 Celery broker”还是“正在等待执行资源”？API、前端和运维口径必须统一。
  7. 部分成功：部分 criterion 失败时任务仍 succeeded 是否符合调用方预期？是否需要 partial_success 或稳定的 quality 字段判断。
  8. 检索控制：函数内一次性 limiter 是否应该删除以避免误导，还是提升为 retriever 级共享 limiter？
  9. 恢复范围：是否接受只恢复 criterion，不恢复 ingest/build_index/plan？
  10. 质量门槛：发布前采用哪些真实合同召回率、准确率、可见批注有效率和耗时阈值？
