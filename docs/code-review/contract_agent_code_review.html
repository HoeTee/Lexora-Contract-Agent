调度

模型槽等待如何向合同队列传播

1. 合同被领取Celery 执行槽从空闲变为占用，任务进入 workflow。
2. criterion 等待资源调用者最多等待 Redis 模型槽 600s；这不是回到 Celery 队列等待。
3. Worker 仍为 busy即使没有发出 HTTP 请求，该合同仍占用一个 Worker 执行槽。
4. 新合同无法开始若 3 个 Worker 都停在资源等待，后续合同只能继续滞留 broker。
容量含义：全局 LLM 上限保护了外部模型服务，但不会自动释放 Celery 合同执行槽。它把过载从“模型在途请求”转化成“运行中合同内的槽等待”。

05 / TIME & RETRIES

时间、租约、等待与重试关系

时间配置必须先按作用对象分类。“等待 600s”“租约 600s”和“请求运行 120s”虽然单位相同，但控制的是不同生命周期。

时间层当前值开始计时到期效果不代表什么
pending 状态检查60s任务记录建立后watchdog 可把长期未投递/未领取任务标为失败不是 Celery broker 消息 TTL
queued 状态检查7200sAPI 标记 queued 后仅对尚未被 Worker claim 的任务进行超时收敛不是 running 合同的总 deadline
模型槽等待600s调用 Redis acquire 后拿不到槽则抛出 semaphore timeout不是 HTTP 请求最长运行时间
模型槽租约600s取得 Redis 槽后到期记录可被清理，其他调用者可取得槽不会自动终止仍在运行的 HTTP 请求
Agent HTTP attempt30sSDK 发起一次模型调用后客户端 attempt 超时，随后可能进入 SDK/外层重试不是 criterion 或合同总耗时
DocxIndex HTTP attempt120s同步客户端发起一次 LLM/embedding 请求后本次 attempt 超时；下一次重试会重新等槽不是整个 complete()/检索调用耗时

Broker visibility timeout未显式配置Worker 领取消息后实际行为依赖当前 Celery/Redis transport 的有效默认值静态材料不能假定它必然覆盖最长合同任务
图 2：时间参数必须按作用对象区分；队列超时、槽位等待、租约和 HTTP timeout 不能互相替代。

租约必须覆盖单次请求，而不是反过来截断请求

并发安全不变量： T_lease ≥ T_http_attempt_max + T_cancel_cleanup + safety_margin

当前项目可静态确认 600s > 120s。取消后上游服务端实际还会运行多久，不确定；项目代码无法证明服务端已经停止，因此需要保留清理余量并通过服务端指标验证。

t = 0s调用者取得一个 Redis 槽，开始单次 HTTP 请求。假设请求上限被改为 1000s。
t = 0～600s请求仍在运行，Redis 租约有效；该请求正确计入全局并发上限。
t = 600s租约过期，但 HTTP 请求不会因此被自动取消；Redis 认为这个槽已经可回收。
t > 600s新调用者可取得同一容量名额，旧请求仍在途，真实并发可能突破配置上限。
冲突结论：如果将单次模型请求上限设置为 1000s，而租约仍为 600s，问题不是“请求最多只能运行 600s”，而是“600s 后请求可能继续运行但不再被全局计数”。这会破坏并发上限的真实性。

时间配置联动检查

单次请求安全：lease ≥ max(Agent attempt, DocxIndex attempt, 其他复用同一 key 的 attempt) + 清理余量
逻辑调用包络：Σ(每次槽等待 + 每次 HTTP attempt + retry backoff)
合同任务包络：索引构建 + Planner + 并发 criterion 墙钟时间 + 汇总/报告；不能把并发 criterion 耗时直接相加
仍需补齐的部署声明：task_queue/celery_app.py 当前只显式配置序列化、时区、started 状态和 prefetch；没有显式声明 task hard/soft time limit 或 Redis broker visibility timeout。若合同允许运行数小时，应把这些有效值纳入部署配置和启动日志，而不能依赖未记录的依赖默认值。

重试放大

DocxIndex LLM 的同步客户端对 429 最多执行 5 次尝试，并使用 1、2、4、8 秒退避；每次尝试都会重新等待全局模型槽。结构化输出校验默认还允许 3 轮完整调用。

DocxIndex complete() 理论配置包络 ≤ 5 × (600s 槽等待 + 120s HTTP) + 15s 退避 = 3615s
complete_model() 理论配置包络 ≤ 3 × 3615s = 10845s
这些是把所有上限同时取满的配置包络，不是实际延迟预测。429 通常会提前返回；缓存命中、有效输出和快速响应都会显著缩短时间。材料不把包络值冒充实测 SLA。

其他乘法层

  • chat_until_valid_json(max_attempts=3)：Agent 结构输出失败时最多 3 次逻辑聊天。
  • criterion_retry_max_attempts=2：一条 criterion 的完整检索、审查和反思链可能整体重跑。
  • max_reflection_rounds=3：非 compliant 结果可能进入多轮 Reflector。
  • Agent 的 OpenAI SDK max_retries=1：具体退避由已安装依赖实现决定；只从项目代码无法确定精确总时间。

rulePlanner 明确给出的精确 terms全文精确短语/规则扫描命中 anchor；全未命中时返回确定性说明不是 BM25，不自行扩展近义词。
region一个 region 或一个标题定位器限定范围后完整读取或语义检索范围内 node 和原文 anchor不得自动退回全局检索。
scancriterion、可选 region所有非空 anchor 按 token 分批，由线程池调用 LLMLLM 确认的 anchor finding任一批失败不能声称全文扫描完成。
hybrid无法预先限定范围的 query全局结构语义 + 向量补充 + rerank全局相关 node本身是执行路线，不是 fallback 别名。

Fallback 与反思重检

检索 fallback

只有配置启用、RoutePlan 明确请求且路线仅含可安全扩大的 title/rule 时，才补一次全局语义检索。region/scan/hybrid 不触发。

反思重检

第一轮证据不足后，审查 Agent 以新的缺口 query 再调用 contract_search。它属于新一轮取证，不等同于当前检索的 fallback。

检索设计风险

  • llm_query() 对结构分片仍按顺序循环；内部 BoundedSemaphore 不会让这些分片并发。
  • rerank_matches() 每次调用只产生一个 LLM 请求，函数内新建 limiter 不形成跨 criterion 控制。
  • DocxIndex rerank 使用通用 LLM，不使用配置中的专用 reranker provider。
  • 多 region 的交错合并至少保留每个非空步骤的一项，但最终证据质量仍依赖结构摘要和模型选择。
  • 索引快照持久化用于复现和恢复；在线 retriever 的内存对象仍与单次 MCP 进程生命周期绑定。

11 / DEPLOYMENT & CAPACITY

部署边界与容量推演

当前容器边界

  • API：1 个 uvicorn worker。
  • Celery：3 个独立 worker 容器，每个 concurrency 1。
  • Redis DB 0：Celery broker。
  • Redis DB 2：模型 semaphore。
  • 共享 ./data：任务状态、输入、输出、日志、索引快照。

扩容时必须同步复算

  • 增加 worker 会线性提高合同与 criterion 生产并发。
  • 不提高 Redis 模型上限时，新增 worker 更容易停在模型槽等待。
  • 提高全局模型上限前需确认上游服务配额、QPS 和显存容量。
  • 共享数据目录必须支持多个容器一致读写和锁文件语义。
吞吐瓶颈 ≠ max(worker)；吞吐瓶颈 = 各阶段有效服务率中的最小值

在当前配置下，仅增加 Celery worker 数量不会必然提高模型密集阶段吞吐，因为 LLM 全局在途上限仍为 5。反之，只增大 LLM 全局上限也不保证合同吞吐增加，因为合同执行槽仍为 3，且 DOCX 解析、索引和报告生成还会占用 CPU/内存。

12 / REVIEW QUESTIONS

建议在内部评审会上确认的问题

  1. 容量目标：目标是限制全局在途请求、每秒启动次数，还是同时限制两者？当前只有全局在途限制，没有统一全局 QPS limiter。
  2. 合同并发：max_api_concurrent_reviews=100 是否应在队列模式下保留，还是应明确标注只对进程内模式生效？
  3. 模型分类：DocxIndex rerank 应继续使用通用 LLM，还是改用专用 reranker 并消费 reranker semaphore？
  4. 超时策略：Agent 30s 与 DocxIndex 120s 是否是有意区分？是否需要统一的“单次 HTTP、逻辑调用、criterion、任务”四级 deadline？
  5. 等待策略：允许 Celery worker 最多等待模型槽 600s 是否合理？是否应把等待移到不占用合同 worker 的调度层？
  6. 状态语义：queued 是“已进入 Celery broker”还是“正在等待执行资源”？API、前端和运维口径必须统一。
  7. 部分成功：部分 criterion 失败时任务仍 succeeded 是否符合调用方预期？是否需要 partial_success 或稳定的 quality 字段判断。
  8. 检索控制：函数内一次性 limiter 是否应该删除以避免误导，还是提升为 retriever 级共享 limiter？
  9. 恢复范围：是否接受只恢复 criterion，不恢复 ingest/build_index/plan？
  10. 质量门槛：发布前采用哪些真实合同召回率、准确率、可见批注有效率和耗时阈值？
