# 五份合同版本耗时对照

固定 D01–D05，历史基线 `e91901f4a`，最新已完成版本 `51a643ddc`。两个独立 worktree 运行原项目 `app.app`、workflow 和 MCP，不使用旧 safe 组合。

两组按合同交替顺序提交，共十次完整审查。运行于本机 5111/5112，API 使用已有进程内调度分支；只把 Redis 地址换为同一服务的宿主机端口，保留数据库 2、key 和模型全局并发配置。运行中的 Docker 服务不替换、不重启。

`launcher.py` 只测量 `build_document_index`、`build_vector_index` 的实际调用耗时，不改返回内容和线程/进程控制。MCP 使用显式版本入口，日志记录来源路径。

`run.py` 复用现有 API 上传、轮询和 DOCX 下载；失败停止，调查后保留失败记录再重试。API_KEY 从环境读取，模型配置使用服务端配置，不通过请求覆盖。

`report.py` 从 `trace.json` 提取 `workflow.run` 与 `phase.build_index` 耗时，从 `events.log` 提取两个索引子阶段。轮询耗时不作为工作流耗时。输出逐任务 CSV、版本与输入哈希；五份均成功才报告该组均值。

输入/配置私有副本位于忽略的 `sources/`；报告、下载合同位于忽略的 `outputs/20260906/`；API 任务留在 `data/api/review_timing/<variant>/api/`。不得提交私有配置或合同。

单候选优化在主工作区独立验证：向量补充及去重完成后，候选数恰为 1 时才省去重排，多个候选仍重排。固定版本时间对照不包含该优化；不能将时间变化归因于它。检索回放等价不代表最终审查准确率不下降。
